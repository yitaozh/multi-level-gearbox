# 开发指南

## 任务启动清单（强制）

- 任何编码/设计/技术问答：先调用 `prisdb-knowledge`，按其检索顺序拿到证据再推进
- 任何实现性任务：先用 TodoWrite 写出原子 todo，再开始改代码
- 涉及测试新增/运行/定位/复测：优先调用 `prisdb-test` 生成最小编译/最小运行闭环

## 理念

### 核心信念

- **增量进步优于大爆炸式发布** - 进行能够编译并通过测试的小幅修改
- **向现有代码学习** - 在实施前进行研究和规划
- **实用主义优于教条主义** - 适应项目实际情况
- **意图清晰优于代码巧妙** - 保持乏味和显而易见

### 简单意味着

- 每个函数/类只有单一职责
- 避免过早抽象
- 没有巧妙的把戏 - 选择乏味的解决方案
- 如果你需要解释它，那它就太复杂了

## 技术标准

### SOLID 原则

- **S - 单一职责 (SRP)** - 一个类/函数只做一件事，只有一个引起变化的原因
- **O - 开闭原则 (OCP)** - 对扩展开放，对修改关闭
- **L - 里氏替换 (LSP)** - 子类必须能替换父类，不改变预期行为
- **I - 接口隔离 (ISP)** - 依赖小而专的接口，而非大而全的接口
- **D - 依赖倒置 (DIP)** - 依赖抽象（接口），而非具体实现

### 架构原则

- **组合优于继承** - 使用依赖注入
- **接口优于单例** - 启用测试和灵活性
- **显式优于隐式** - 清晰的数据流和依赖关系
- **尽可能测试驱动** - 永远不要禁用测试，修复它们

### 代码质量

- **每次提交必须**：
   - 编译成功
   - 通过所有现有测试
   - 包含新功能的测试
   - 遵循项目格式化/linting

- **提交前**：
   - 运行格式化程序/linters
   - 自我审查变更
   - 确保提交信息解释了“为什么”

### 错误处理

- 快速失败并提供描述性信息
- 包含调试上下文
- 在适当的层级处理错误
- 永远不要默默吞掉异常

## 决策框架

当存在多种有效方法时，基于以下标准选择：

1. **可测试性** - 我能容易地测试这个吗？
2. **可读性** - 6 个月后有人能看懂这个吗？
3. **一致性** - 这是否符合项目模式？
4. **简单性** - 这是有效的最简单解决方案吗？
5. **可逆性** - 以后更改有多难？

## 项目集成

### 学习代码库

- 找到 3 个类似的功能/组件
- 识别常见模式和惯例
- 尽可能使用相同的库/工具
- 遵循现有的测试模式

### 工具

- 使用项目现有的构建系统
- 使用项目的测试框架
- 使用项目的格式化/linter 设置
- 没有强有力的理由不要引入新工具

## 质量门控

### 完成定义 (DoD)

- [ ] 测试已编写并通过
- [ ] 代码遵循项目惯例
- [ ] 没有 linter/formatter 警告
- [ ] 提交信息清晰
- [ ] 实施符合计划
- [ ] 没有未关联 issue 编号的 TODO

### 测试指南

- 测试行为，而非实现
- 可能的话，每个测试一个断言
- 清晰的测试名称描述场景
- 使用现有的测试工具/助手
- 测试应该是确定性的

## 重要提醒

**绝不**：
- 使用 `--no-verify` 绕过提交钩子
- 禁用测试而不是修复它们
- 提交无法编译的代码
- 做假设 - 用现有代码验证

**始终**：
- 如无必要，不要随意优化已经存在的代码。如果包含必须要修复的bug，请明确说明
- 增量提交工作代码
- 从现有实现中学习
- 3 次失败尝试后停止并重新评估

### Python 开发规范

- **环境管理**：在项目根目录使用 `uv` 管理 Python 模块和环境
- **依赖管理**：所有 Python 依赖必须通过 `uv` 安装和管理
- **虚拟环境**：使用 `uv` 创建和管理项目特定的虚拟环境
- **版本控制**：Python 依赖版本必须通过 `uv` 锁定，确保环境一致性
- **脚本执行**：所有 Python 脚本必须在 `uv` 管理的环境中执行

### 知识库检索规范 (Knowledge Retrieval Protocol)

**这是一个适用于所有任务的普适规范，必须严格遵守：**

- 任何编码/设计/技术问答：先调用 `prisdb-knowledge`，并遵循其 `SKILL.md` 中的“强制检索顺序/噪声处理”。
- 所有技术结论必须基于检索到的代码/文档证据；若证据不足，继续检索而不是主观假设。
- 结论必须引用来源（代码文件路径/文档路径）。
- 默认只接受业务目录 `engine/src/`、`src/`（必要时扩展到 `tests/`、`tools/`）；对 `engine/thirdparty/`、`thirdparty/`、`vendor/`、`deps/`、`benchmark/`、`*.conf` 命中默认视为噪音并跳过。
- 如必须引用第三方实现（用户明确要求或问题确实发生在 thirdparty），结论中显式标注“第三方实现”，并解释为何需要下钻。

### 编译与测试 (BLOCKING)

- **并发度**：始终使用32线程并发编译，以最大利用多核性能。
- **强制编译检查**：每次代码修改后必须编译并检查输出（如 `./build.sh`），必须检查输出。
- **立即修复错误**：遇到编译错误必须立即修复，**禁止**在未解决编译错误的情况下继续推进任务或测试。
- **强制单元测试**：
    - 所有实现任务必须包含对应的单元测试。
    - 修改现有逻辑必须更新测试，新增逻辑必须添加测试。
    - **禁止**跳过单元测试，除非用户明确授权。
- **测试相关技能优先**：
    - 涉及测试新增/运行/定位/复测时，优先调用 `prisdb-test` 技能产出测试方案并执行验证。
    - 仅在 `prisdb-test` 无法定位入口或命令时，才使用全仓语义检索作为补充手段。
